# CodexUsageBar v0.6 开发方案（评审稿）

> 状态：待评审 · 2026-07-22
> 基线版本：v0.5.0 Build 11
> 评审目的：确认四个提案的取舍与优先级后再动工

## 背景与现状评估

v0.5.0 之后，这个 App 的"显示"能力已经基本完整：双窗口百分比、恢复时间轴、耗尽预估、Token 活动热力图、套餐与 Credits、通知、自动更新。继续堆展示项的边际收益递减。

在写本文档前做了三项实测，直接改变了方案设计：

其一，**配额换算不可行**。曾设想把 used_percent 换算成绝对 token 配额（"本周已用 45M / 77M"）。用本机 13,260 条真实 token_count 事件回归 Δused% 与 Δtokens 的关系，尝试六种加权组合（缓存 1 折、输出 5 倍等定价模型），短窗口配额估算离散度 79%~82%（n=2587），周窗口 169%~179%（n=1260），无一收敛。结论：服务端限流不是客户端可重建的简单 token 桶，任何绝对配额数字都是编造精确感。此提案枪毙。

其二，**固定速率阈值必然误报**。统计了历史 15 分钟窗口的消耗突增分布：短窗口 p50=11%、p90=31%、p99=88%；周窗口 p50=3%、p90=7%、p99=24%。短窗口的日常消耗就能达到 31%/15min（p90），任何"速率超过 X%/min 就报警"的设计都会在正常使用时狂响。因此提案 A 改为**续航（runway）模型**——不看速率绝对值，看"按当前速率还能撑多久"。

其三，**Credits 余额已在记录**。`UsageHistoryStore.Record` 已含 `creditsBalance` 字段，history.json 持续积累，提案 D 的观察期零成本。

下一阶段的价值在两个方向：数据源变化时依然正确（生存），和比用户先发现问题（差异化）。以下四个提案按此展开。

---

## 提案 A：续航耗尽预警（Runway Alert）

### 问题定义

现有低用量通知（≤20% 阈值）是马后炮：对跑飞的 agent，20 分钟就能烧穿 5 小时窗口，收到 20% 通知时额度已经死了。重置倒计时通知（5 分钟）只解决"快恢复了"，不解决"快烧完了"。

真正有用的警报是：**"按当前消耗速率，短窗口约 25 分钟后耗尽"**——在用户还来得及停手的时候拦截。

### 为什么用续航模型而不是速率阈值

见背景实测：短窗口 p90 消耗 31%/15min，速率分布极宽，绝对阈值无法区分"正常重度使用"和"失控"。续航模型天然自适应：

- 正常重度使用：剩 60%，速率 1%/min → 续航 60 分钟 → 不报警（用户清楚自己在干什么）。
- 失控循环：剩 60%，速率 4%/min → 续航 15 分钟 → 报警。
- 闲置：速率 ≈ 0 → 续航 ∞ → 不报警。
- 低剩余但已停手：剩 5%，速率 0 → 不报警（没有正在发生的损失）。

警报只在"正在以不可持续的速度消耗"时触发，这正是它该说话的场合。

### 算法设计

**速率计算**（数据源：history.json，60 秒采样，`Record.timestamp` 为事件时间）：

1. 取目标窗口（short / week 各自独立）最近 15 分钟内 `remaining` 非空的记录。
2. 从最新记录向前回溯当前单调消耗段：只要 `records[i-1].remaining >= records[i].remaining`（时间更早、剩余更多 = 正常消耗）就继续；遇到 `records[i-1].remaining < records[i].remaining`（剩余跳涨 = 窗口已重置）即截断。
3. 速率 = (段首 remaining − 段尾 remaining) / (段尾时间 − 段首时间)，单位 %/min。
4. 有效性门槛：段跨度 ≥ 5 分钟、≥ 3 个采样点、速率 > 0.2%/min（地板值，滤除噪声级波动）。不满足则视为无有效速率，不报警。

用事件时间而非墙钟时间是刻意选择：闲置期间 updatedAt 冻结，多条记录时间戳相同，Δt=0 自然被门槛滤掉；只有活跃消耗期才产生有效速率。这正是预期语义——续航预警只关心"正在烧"。

**触发条件**（每个窗口独立判定）：

```
有效速率存在 && remaining / rate <= 30 分钟
```

30 分钟阈值依据：短窗口总量 300 分钟，30 分钟续航 = 窗口时间的 10%，足够用户收尾当前任务；与重置倒计时（5 分钟档）错开一个数量级，不重叠。该值做成常量，预留调整空间。

**去重与冷却**（沿用 `UsageNotificationManager.scheduleResetCountdown` 的成熟模式）：

- UserDefaults 键：`runwayAlert.<kind>.<resetAt 时间戳>`，与重置倒计时的 `resetCountdown.<kind>.<resetIdentifier>` 同构。
- 同一窗口实例（resetAt 不变）只报一次；窗口重置后 resetAt 变化，自动获得新的报警资格。
- 这比固定时间冷却更合理：一次失控 = 一条警报，不会每 30 分钟重复打扰，也不会在窗口轮换后漏报新一轮失控。

**通知文案**：

| 键 | 中文 | English |
|---|---|---|
| runwayAlertTitle | 用量消耗过快 | Usage Burning Fast |
| runwayAlertBodyShort | 按当前速率，短时窗口约 %@ 分钟后耗尽 | At the current rate, the short window runs out in about %@ minutes |
| runwayAlertBodyWeek | 按当前速率，每周窗口约 %@ 分钟后耗尽 | At the current rate, the weekly window runs out in about %@ minutes |

分钟数取整到 5 的倍数（"约 25 分钟"比"约 23 分钟"更诚实，因为速率本身是估计值）。

### 改动点

| 文件 | 改动 |
|---|---|
| `UsageNotificationManager.swift` | 新增 `evaluateRunway(snapshot:historyStore:language:enabled:)` 与私有 `scheduleRunwayAlert(window:kind:runwayMinutes:language:)`；速率计算抽为纯函数 `static func runwayMinutes(records:window:) -> Int?` 便于测试 |
| `CodexUsageBarApp.swift` | 现有 `store.$snapshot` sink 中，与 `evaluateResetCountdown` 并列调用 `evaluateRunway` |
| `Localization.swift` | 新增上表三个键 |
| `Tests/ModelTests.swift` | 速率纯函数回归测试（见测试计划） |

不新增文件、不改数据模型、不动 UI——纯通知层扩展。

### 边界情况

| 情况 | 行为 | 依据 |
|---|---|---|
| 刚启动，历史不足 3 点 | 不报警 | 门槛不满足 |
| 窗口刚重置（剩余跳涨） | 单调段截断，旧速率作废 | 步骤 2 |
| 剩余已 <20% 且仍在高速消耗 | 续航预警与阈值通知可能同时触发 | 可接受：两条通知语义不同（"快烧完了" vs "已经很低"），且都指向同一行动 |
| 用户关闭通知总开关 | 不报警 | `enabled` 参数透传，与现有行为一致 |
| 两个窗口同时满足 | 各报一条 | 独立判定，罕见（周窗口 p99 才 24%/15min） |

### 测试计划

`runwayMinutes` 是纯函数，用构造记录序列覆盖：正常消耗段算出预期续航；含重置跳变的序列只在最新段计算；跨度不足 / 点数不足 / 速率为零返回 nil；边界值（续航恰好 30 分钟）行为明确。

### 工作量

约 5~6 小时（含测试与真机验证）。

## 提案 B：反静默腐化（Anti-Silent-Rot）

### 问题定义

这个 App 的命脉是解析 OpenAI **未公开、未承诺稳定**的本地日志格式。格式漂移已有先证：`rate_limits` 的 primary/secondary 命名不一致（primary 可能是 300 分钟短窗口，也可能是 10080 分钟周窗口，secondary 常为 null），现在靠 `window_minutes` 分类兜着。下一次格式变更是必然事件。

腐化的两种形态：解析直接失败（App 报错，用户知道，**可接受**）；解析出残缺数据——事件能读但 rate_limits 结构变了，菜单静默显示 "H --% W --%" 或冻结在旧值（**不可接受**，正是上次 4% vs 99% 事故的同类）。

目标：App 自己先于用户发现格式漂移，并明确说出来。

### 第一层：运行时漂移检测

**信号定义**：session 文件持续在更新（最新 mtime 距现在 ≤ 10 分钟 = 用户在活跃使用 Codex），但连续 2 次刷新都解析不出有效 snapshot（或解析出的 snapshot 双窗口全空）。

 idle ≠ drift：用户没在用 Codex 时文件不更新，解析不出新数据是正常的，绝不计数——这是防误报的关键约束。

**实现要点**：

`CodexUsageProvider` 是 struct（值类型），不持有状态。计数器放在 `UsageStore`（class）：

1. `readLatestSessionUsage` 的返回从 `UsageSnapshot?` 改为枚举：

```swift
enum SessionReadResult {
    case success(UsageSnapshot)
    case driftSuspected(latestFileModification: Date)  // 文件新鲜但无可解析事件
    case noData                                         // 无文件或文件陈旧
}
```

2. `fetchUsage` 保持协议签名不变，但新增只读属性暴露本次读取是否疑似漂移——由于 struct 限制，改为让 `UsageSnapshot` 增加 `sessionDriftSuspected: Bool` 字段（默认 false，Mock 与 header 路径均为 false）。这是最小侵入方案：值语义天然随 snapshot 流转，UsageStore 无需感知 provider 内部。

3. `UsageStore.refresh()` 维护 `consecutiveDriftCount`：snapshot.sessionDriftSuspected 为 true 则 +1，否则归零。≥2 时设置新的 `providerError = .schemaDrift`（新增错误枚举 case）。

4. 展示：`detailMessage` 显示漂移警告文案；菜单栏标题不额外加符号（已有 ⚠︎ 机制由 isStale 管，语义不混用）。

**文案**：

| 键 | 中文 | English |
|---|---|---|
| schemaDrift | 会话日志格式可能已变化，数据可能不准确。请检查 App 更新。 | Session log format may have changed; data might be inaccurate. Check for app updates. |

**为什么是连续 2 次而非 1 次**：文件正在被写入的瞬间可能读到截断的行，单次失败有合理替代解释；连续 2 次（间隔一个刷新周期，默认 30 秒以上）基本排除瞬态。

### 第二层：离线回归 Fixture

把"当前格式长什么样"钉死在测试里。格式变了 → 测试红 → 修解析器、加新 fixture，而不是等用户上报。

**零重构优势**：`CodexUsageProvider.init(databasePath:sessionsPath:)` 已支持路径注入，`readLatestSessionUsage(at:)` 接受任意根目录。fixture 测试直接：

```swift
let provider = CodexUsageProvider(sessionsPath: fixturesDir.path)
let snapshot = try await provider.fetchUsage()
expect(snapshot.weekWindow?.remainingPercent == 98, "...")
```

**Fixture 制作**：从真实日志各抽 2~3 条事件，只保留解析所需字段（`timestamp`、`payload.type`、`payload.info.last_token_usage`、`payload.rate_limits`），丢弃其余——token_count 事件本身不含路径、对话内容等隐私，但时间戳归一化为固定值保证测试确定性。必须覆盖的 case：

1. primary = 短窗口（300min）、secondary = 周窗口（10080min）——标准布局。
2. primary = 周窗口、secondary = null——命名反转布局（真实存在，见 MEMORY 记录的历史事故）。
3. 含 `plan_type` + `credits`（has_credits/unlimited/balance 三种形态：数字余额、unlimited、无 credits）。
4. 一条"未来格式"占位：rate_limits 为空对象 → 断言解析出双窗口全 nil 的 snapshot 而非崩溃（残缺数据兜底行为）。

**集成**：fixture 放 `Tests/Fixtures/`，`scripts/test.sh` 的编译列表已含 `CodexUsageProvider.swift`，只需在 `ModelTests.swift` 加测试函数并在编译命令中传入 fixture 目录（通过 ProcessInfo 环境变量或硬编码相对路径——测试二进制在 build/ 下运行，用 `#filePath` 定位 Tests/ 目录最稳）。

### 边界情况

| 情况 | 行为 |
|---|---|
| 用户活跃使用但恰好 10 分钟内无 token_count 事件（纯浏览无请求？） | 理论上可能误计 1 次漂移；连续 2 次门槛挡住 |
| SQLite 备用源正常、session 漂移 | snapshot 来自 header（置信行显示"响应头备用"），同时漂移警告浮现——两个信号叠加正是诊断所需 |
| 格式变更后又恢复（OpenAI 回滚） | 下一次成功解析即归零计数，警告自动消失 |

### 工作量

约 4~5 小时（枚举改造 1.5h + 计数与展示 1h + fixture 与测试 2h）。

## 提案 C：菜单栏单值模式

### 问题定义

"H 98% W 98%" 需要用户解码 H/W 含义，占两个身位。菜单栏的本职是"瞥一眼"，最紧张的那个窗口才是唯一需要瞥的信息。

### 设计

`AppSettings` 新增（沿用 `showShortWindow` 的 `@Published` + `didSet` 持久化模式）：

```swift
enum MenuBarMode: String { case dual, worst }
@Published var menuBarMode: MenuBarMode {
    didSet { defaults.set(menuBarMode.rawValue, forKey: Keys.menuBarMode) }
}
```

`updateStatusButton()` 分支：

- `dual`：现状不变（H/W 双段，受 showShortWindow/showWeekWindow 开关控制）。
- `worst`：取 `snapshot.featuredWindow`（已存在，算法为剩余最低者），只显示 "98%"，颜色仍走 `UsageColorLevel` 三色规则，⚠︎ 过期标记保留。无 snapshot 时显示 "--%"。

**信息不丢失的补偿**：`button.toolTip` 从固定的 "CodexUsage" 改为动态完整状态 "H 98% · W 98% · 更新于 11:40"——悬停即见全量，单值模式不牺牲任何信息。

**设置 UI**："菜单栏显示"子菜单重构为：

```
显示模式  ▸  ◉ 双窗口   ○ 单值（最紧张）
☑ 短时窗口      ← 仅 dual 模式启用
☑ 每周窗口      ← 仅 dual 模式启用
```

worst 模式下两个窗口开关置灰（`isEnabled = false`），避免"开关存在但不生效"的困惑。

### 默认值

新装默认 `dual`（不改变现有用户预期）。这是审美取舍而非对错问题——但根据你过往的减法倾向，你大概率会切到 worst；做成可切换就把选择权留下。

### 工作量

约 2 小时。

## 提案 D：Credits 消耗追踪（观察先行，暂不开发）

### 现状

`UsageHistoryStore.Record.creditsBalance` 已在每次采样时记录（`snapshot.credits?.displayBalance`），history.json 保留 7 天。**数据积累零成本，已经在发生。**

### 为什么先观察

Credits 余额（你账号当前 2500）是否随使用真实变动，无法从静态代码确认。如果 Plus 套餐的 balance 是静态配额展示（从不减少），整个功能对你的账号毫无意义，不该写一行代码。

### 决策标准

一周后检查 history.json：`creditsBalance` 出现过 ≥2 个不同数值 → 立项；始终单值 → 关闭提案。

### 预案设计（仅当立项时执行）

- `Record` 已存 balance 字符串，解析为 Double 防御性处理（格式未知，可能是 "2500" 或 "25.00"）。
- 摘要行 "套餐: Plus · Credits 余额: 2500" 扩展为 "… · 本周 −120"（本周最早记录 − 最新记录）。
- 可选：余额按 7 日线性趋势的续航估计，复用提案 A 的单调段算法。
- 工作量约 2 小时。

## 明确不做（及理由）

**配额换算**——实测枪毙，见背景。离散度 79%~179%，做出来就是撒谎。

**Scraping 官方 Usage 页面 / 读取 cookie 或 auth.json**——RELEASE_NOTES 的隐私承诺是这个 App 在同类工具里的品牌定位（"数据源完全位于本机"），破坏它换来的功能增量（更"权威"的百分比）抵不过信任损失。

**独立 dashboard 主窗口**——菜单栏工具的灵魂是不索取注意力。热力图已经是菜单信息密度的上限，再扩张就变成另一个需要被管理的应用。

**多机同步、更多语言、插件系统**——受众是 Codex CLI 用户，三个都是伪需求，复杂度却是真实的。

## 实施顺序与版本规划

| 顺序 | 提案 | 性质 | 工作量 |
|---|---|---|---|
| 1 | B 反静默腐化 | 生存基础，越晚做风险敞口越大 | 4~5h |
| 2 | A 续航耗尽预警 | 最高用户可见价值 | 5~6h |
| 3 | C 单值模式 | 质感打磨 | 2h |
| 4 | D Credits 追踪 | 观察期数据说了算 | 2h（条件触发） |

A+B+C 合计约 1.5 个工作日，合并发布为 **v0.6.0**。B 先行的理由：A 的通知逻辑建立在"数据可信"之上，如果格式漂移了，续航预警会基于垃圾数据乱报——先保证地基，再盖楼。
